# Linux VST3 native editor hosting

- Status: review_pending (XWayland runtime exercised against DISTRHO MVerb; user review and native-Wayland-only fallback review open)
- Scope version and requirement IDs: Linux VST3 native editor support, first stage `linux-vst3-editor-v1`.
- Desired observable outcome: A Linux x86_64 user on X11 or XWayland can open the plug-in's native VST3 editor from an insert; parameter fallback remains available when no supported native view exists. Native Wayland-only sessions report a clear limitation.
- Reference evidence: User direction to close the Linux editor gap; existing `T045`/`T046`; VST3 `IPlugView` platform type `kPlatformTypeX11EmbedWindowID`; OpenTrack selects X11/XWayland when `DISPLAY` is advertised. The host window/child/XEmbed event flow was checked against [Steinberg's Linux VST3 editor-host sample](https://github.com/steinbergmedia/vst3_public_sdk/blob/master/samples/vst-hosting/editorhost/source/platform/linux/window.cpp), [platform UI type documentation](https://steinbergmedia.github.io/vst3_doc/base/group__platformUIType.html), and [Steinberg's Linux IRunLoop host contract](https://steinbergmedia.github.io/vst3_dev_portal/pages/Technical%2BDocumentation/Provide%2BA%2BRunloop%2BOn%2BLinux/Index.html), which makes `IRunLoop` queryable from the host context and `IPlugFrame`. The implementation is original Rust code.
- Dependencies and decisions needed: Use the existing X11 connection stack (x11rb is already in Cargo.lock through the GUI stack); do not add a plug-in framework. Confirm the VST3 Linux X11 embed contract against the VST3 bindings and native runtime.
- Code scope and architecture boundaries: `opentrack-app/src/vst3_host.rs` owns the Linux editor window/thread/message loop; `opentrack-vst3/src/editor.rs` owns native view attach/resize/detach with X11 window IDs; `opentrack-vst3/src/host.rs` and `services.rs` expose one shared Linux `IRunLoop` through both `IHostApplication` and `IPlugFrame`, dispatching FD/timer callbacks on the editor thread. The host uses a decorated top-level plus a separate plug-in parent child window; plug-in child creation is observed asynchronously, the plug-in's `_XEMBED_INFO` version is read, and the host sends embed/activate/focus notifications. No VST3/platform types in core/project state. Keep current Windows implementation unchanged.
- Acceptance checks: Linux build; real plug-in reports X11EmbedWindowID, receives a valid parent XID, paints, takes keyboard focus, responds to pointer editing, resizes, and closes/reopens without crashing. Verify one real third-party Linux VST3 editor; native Wayland-only fallback must remain explicit. Additional plug-ins and user review broaden confidence beyond the tested module.
- Affected regressions: insert selection, parameter fallback, project dirty state from native editor edits, editor-thread isolation and close behavior, Windows editor lifecycle.
- Essential gates: native build and a real Linux plug-in are required for runtime claims; compile-only checks do not establish editor interoperability.
- Review owner and milestone stop: User review after a native Linux plug-in session; record each plug-in/version tested.

- Failures/unknowns/pending acceptance: Runtime coverage is one DPF-based module on XWayland, not a universal compatibility claim. Native Wayland `WaylandSurfaceID`/`IWaylandHost` remains unsupported. The VST3 3.8 contract requires a native Wayland host to implement `IWaylandHost::openWaylandConnection`, act as a compositor for the plug-in connection, and pass a parent `wl_surface` on which the plug-in creates a `wl_subsurface`; it is not satisfied by passing OpenTrack's system-compositor surface. See [Steinberg's Wayland frame contract](https://steinbergmedia.github.io/vst3_doc/vstinterfaces/group__waylandFrame.html) and [platform UI type contract](https://steinbergmedia.github.io/vst3_doc/vstinterfaces/group__platformUIType.html). The Wayland server crate was fetched and evaluated, then removed from product dependencies because it alone does not provide compositor rendering/input integration. Casilda offers a GTK4/wlroots compositor widget for Wayland client embedding, but adopting it would add GTK/wlroots runtime and packaging requirements to the current egui/winit app; it is not currently selected ([Casilda 1.0 design and API](https://blog.gtk.org/2025/09/15/casilda-1-0-released/)). The no-X11 display guard has a focused regression test for missing, empty, and present `DISPLAY`, but that tests the reported fallback only, not operation in a native-Wayland-only desktop session. Host-level tests prove timer/FD dispatch and unregister behavior, and both host context and frame share the same run loop; MVerb itself did not establish that a real plug-in registered or fired these callbacks. End-to-end project save/dirty behavior through the full app remains unverified, as does broader plug-in compatibility. MVerb emitted DPF warning “asked to delete component while audio processor still active (refcount 1)” after OpenTrack received `kResultOk` from `setProcessing(false)`, `setActive(false)`, controller terminate, and component terminate. The identical warning appears in [DPF issue 372](https://github.com/DISTRHO/DPF/issues/372) during an initialization-abort path. This suggests a DPF diagnostic independent of a failed host teardown call, but does not prove the warning harmless; keep it visible pending another plug-in or DPF source-level confirmation. An OpenTrack window was launched on XWayland and its menu shell rendered. The window opened without a project; KWin's Remote Control prompt blocked automated input before the example project or insert workflow could be reviewed. The untouched app was closed with a window-manager close request. User review remains pending.

Native Wayland support requires an explicit compositor/runtime architecture and distribution decision; keep the unsupported state clear until that path is built and tested.
