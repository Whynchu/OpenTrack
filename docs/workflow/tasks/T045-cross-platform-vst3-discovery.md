# T045 — Cross-platform VST3 discovery foundation

- Status: review_pending
- Scope version and requirement IDs: future `vst3-platform-v1`; outside the frozen transport scope in `ledger.json`
- Desired observable outcome: The scanner and insert picker locate a bundle's native binary on Windows, macOS, and Linux; default scan folders and CPU architecture checks follow the current host target.
- Reference evidence: User-specified direction: native VST3 appearance and behavior should match the plug-in's own UI, and users on macOS/Linux should be supported. Steinberg's [plug-in locations](https://steinbergmedia.github.io/vst3_dev_portal/pages/Technical%2BDocumentation/Locations%2BFormat/Plugin%2BLocations.html) and [bundle format](https://steinbergmedia.github.io/vst3_dev_portal/pages/Technical%2BDocumentation/Locations%2BFormat/Plugin%2BFormat.html) define the platform folders and binary layouts. Its [module lifecycle](https://steinbergmedia.github.io/vst3_dev_portal/pages/Technical%2BDocumentation/VST%2BModule%2BArchitecture/Index.html) and [editor platform types](https://steinbergmedia.github.io/vst3_doc/vstinterfaces/group__platformUIType.html) remain separate platform-specific work.
- Dependencies and decisions needed: No new dependency introduced. Native module-entry lifecycle, native editor parent surfaces, audio-device backends, and packaging still need platform-specific implementation and native-machine review.
- Code scope and architecture boundaries: `opentrack-plugins` owns host-architecture classification; `opentrack-plugin-scan` owns platform folder defaults, bundle selection, and bounded PE/ELF/Mach-O header reading; `opentrack-app` reuses the scanner's bundle resolver. No VST3 types enter project/core code.
- Acceptance checks: Build the scanner and app for Windows x64, macOS arm64 and x64, and Linux x64. On each native platform, scan a merged bundle and a platform-native bundle, verify the selected binary path and architecture, then enumerate a known VST3. Verify Windows x64's existing Program Files and LOCALAPPDATA roots and insert-picker behavior. macOS/Linux module lifecycle and UI acceptance remain gated on the follow-up packet.
- Affected regressions: Windows x64 still prefers `Contents/x86_64-win`; scanner reporting still includes known Windows architectures when the native x64 directory is absent. Existing runtime results are not evidence for macOS/Linux.
- Essential gates: Native macOS/Linux builds and plug-in scans have not been performed in this Windows workspace. This packet only establishes discovery and image-precheck foundations; it does not claim cross-platform loading or native editor support.
- Review owner and milestone stop: User review after a native-platform build and scan. T046 implemented the macOS `CFBundle` and Linux `ModuleEntry`/`ModuleExit` lifecycles. Hosted compile and native plug-in acceptance remain pending; native editor surfaces (`NSView`, X11/Wayland) and event-loop integration are separate future work.
