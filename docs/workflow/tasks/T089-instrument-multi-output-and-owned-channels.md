# T089 — Instrument multi-output channels and channel-role behavior

- Status: in_progress
- Scope version and requirement IDs: post-revision-5 user-directed feature, version 1.
- Desired observable outcome: a multi-output VST3 instrument can route each output bus to an independently mixable child channel beneath its MIDI-owning Instrument track. Effect channels accept routed audio without record/waveform affordances. Folders remain organizational containers and support nested track structures.
- Reference evidence (IDs/paths; observed vs user-specified vs unknown): user direction on 2026-11-04; MT Power Drum Kit vendor documents eight stereo outputs, initially assigned to Out 1, with each output enabled by the host. The fetched VST3 wrapper negotiates multiple main outputs but currently folds them into one stereo signal. No MT Power Drum Kit binaries or content are available on this machine.
- Dependencies and decisions needed: no packaging or redistribution of MT Power Drum Kit. The MT Power Drum Kit runtime check must happen on the user's other machine. Preserve the legacy single-output instrument/effect path. Out 1 is represented like every other output child; the Instrument parent owns MIDI and receives the child sum for shared level/routing.
- Code scope and architecture boundaries: `opentrack-core` track ownership/serialization/validation and commands; `opentrack-plugins` realtime hosted-output API; `opentrack-vst3` output-bus processing; `opentrack-audio` per-block bus buffers, child channels, routing and PDC; app VST3 instrument assignment/reconciliation, track list/Mixer, record controls, folder behavior; README/native-format/task/current documentation. Keep ownership constraints in core; no callback allocation or locking.
- Acceptance checks (action, expected result, fixtures, evidence to retain):
  1. A synthetic VST3-like processor emits distinct signals on a main and multiple auxiliary mono/stereo output buses; each instrument bus reaches only its matching child channel, and combined output is correct. Ordinary effect instances continue to select the main bus only.
  2. The instrument instance receives MIDI once per block and advances once; output buses are activated independently and not summed twice.
  3. Stable bus IDs and child-channel settings survive save/reopen, plug-in rescan, duplicate, delete and a changed bus layout. Missing/failed plug-ins remain recoverable and do not route to an unrelated bus.
  4. Instrument output children cannot be moved out of or reassigned away from their owner; they can be reordered/renamed within the instrument subtree. They are not recordable waveform tracks.
  5. FX channels expose receive, channel processing and routing but no record/arm or waveform editing. Folders can nest valid track/folder contents, stay non-audio and preserve subtree behavior.
  6. Existing one-bus VST3 effects/instruments and ordinary group/folder routing remain unchanged.
  7. Full relevant core/audio/app tests, formatting, diff check and local-ASIO release build pass; real MT Power Drum Kit bus routing and desktop presentation are explicitly left for the user's other machine/session if unavailable here.
  8. VST3 editor windows are assigned the OpenTrack owner before mapping. Linux X11/XWayland editors use OpenTrack app identity/icon and window-manager activation; native Wayland-only launch reports the embedding limitation clearly.
- Affected regressions: VST3 instrument creation/load/save; callback timing and MIDI delivery; track ownership/move/delete/duplicate; group and folder route validation; mixer/project arrange track controls; OPR migration.
- Essential gates (audible result, persistence, undo/dirty state, recovery as applicable): one plug-in processing call per block; no bus double-counting; PDC preserved; persistent child ownership and settings; failed-load recovery; no recording/waveform affordances on FX/output channels; desktop and audible acceptance by the user.
- Review owner and milestone stop: code and automated verification here; stop for the user's real-plugin listening and desktop review. No user acceptance is claimed by the implementer.
