# Architecture notes

## Product target

OpenTrack- is a standalone Rust DAW prioritizing usable musical workflows close to Cubase 5, with deliberate improvements and independent future plug-in designs. Bundled plug-in recreation is deferred; 1:1 copies are not required. Third-party hosting is separate. See the current [architecture agreement](workflow/architecture-agreement.md) and [workflow](workflow/README.md). Implementation details below are historical notes to revalidate against source. REA and the installed application are evidence sources; they are not runtime dependencies. The first native application target is x86_64 Windows.

## Main subsystems

1. **Command and keymap model** � stable command IDs; window/editor contexts; multiple bindings per command; conflict handling; macros; user-editable profiles and import/export. The Windows profile currently loads 152 commands transcribed from the local manual and dispatches implemented actions through the internal opentrack-core command model.
2. **Workspace and window model** � docked and floating windows, editor visibility and geometry, saved layouts, workspace recall/lock commands, and monitor-aware restoration.
3. **Project model and serialization** � OpenTrack's versioned native format, undoable edits, media references, migration, and recovery. The core owns projects, tracks, WAV references, arrangeable MIDI parts with beat-based note and controller events, cycle locator positions, built-in instrument waveform state, four-band EQ, ordered insert state, and per-track Solo Defeat. The app writes version 18 JSON OPR files and migrates versions 1–17 on open, retaining the earlier native marker for compatibility. Version 18 records the managed-project-folder state. Older versions add cycle locators, MIDI controllers/channels, instrument waveform, workspace preset origin, and Solo Defeat. Managed folders place OPR at the root, imports in `Audio/Imports`, recordings in `Audio/Recordings`, and reserve `Metadata` for generated data.
4. **Audio and MIDI engine** � real-time-safe processing, transport clock, routing, automation, recording, device configuration, and plug-in scheduling. The current opentrack-audio crate decodes smaller mono/stereo WAV sources, streams larger ones through bounded per-clip caches, generates waveforms on a background worker, mixes playback, and processes four-band EQ plus insert effects. On Windows, WASAPI handles endpoint capture and render with shared low-latency, shared-compatible fallback, and opt-in exclusive modes; CPAL remains for endpoint inventory and non-Windows streams. Input testing uses independent channel meters. Track monitor input can pass through the track's processing and output route, and armed audio tracks can record Stereo/Left/Right input routes to separate float WAV takes. Capture timestamps and discontinuity counts are retained. MIDI notes and selected controller events render through selectable oscillator voices supplied by a reusable Rust instrument factory/processor interface. Windows MIDI input uses WinMM for recording and MIDI Thru through the starter oscillator. General typed bus routing, arbitrary device channel maps, endpoint hot-plug recovery, measured latency compensation, MIDI output, automation, and a general plug-in host remain future work.
5. **Historical plug-in prototypes (future design deferred)** � individually scoped original designs with the user, integrated with OpenTrack-'s audio and project-state models. TestGenerator is the first manual-documented effect in the insert chain, but its DSP output has not been compared with Cubase. A general-purpose plug-in ABI and parity-verified bundled rewrite are not yet implemented. Track module paths, behavioral evidence, and rewrite status in [the plug-in inventory](plugin-rewrite-inventory.md).
6. **Compatibility layer** � CPR inspection/import and optional out-of-process support for unrelated legacy 32-bit plug-ins. Keep compatibility paths isolated from the core project and audio models. Current CPR findings and the legacy-hosting gate are documented in [compatibility notes](compatibility-notes.md) and the [legacy plug-in hosting investigation](legacy-plugin-hosting.md).

## Compatibility constraints

- A 32-bit Windows DLL cannot be loaded into the 64-bit process. Future first-party effects are designed independently in Rust for the native host. An x86 helper is relevant only if separate support for original third-party 32-bit binaries is chosen; its IPC and real-time behavior would need design and measurement, and VST 2 distribution has an unresolved licensing gate.
- Treat native Cubase CPR import and round-trip as goals under investigation. Preserve unknown data where practical and report unsupported elements; do not claim compatibility from template samples alone.
- Determine external plug-in APIs and requirements before promising third-party VST2/VST3 compatibility. Rewritten bundled plug-ins do not by themselves establish binary compatibility with Cubase's plug-in ABI.

## UI framework decision

The current prototype uses eframe/egui 0.36.2 and egui_dock 0.21.1 for its Windows desktop shell. The arrange view is in the main window; Mixer, Channel Settings, MediaBay, and MIDI Editor also open as native top-level viewports. The main title follows the current OPR filename. The app has transport controls, reference shortcuts, and native OPR Save/Open. WAV playback, input recording, track mix controls, four-band EQ, a Stereo Delay insert, and selectable WASAPI audio modes are connected in source. Hardware recording and audio-device behavior have not yet been manually accepted on the target device. Window geometry is saved to project workspaces, but visual matching and monitor-aware restoration have not been validated.

The workspace can compile both `x86_64-pc-windows-msvc` and `i686-pc-windows-msvc` in debug and release profiles. x64 remains the primary product target. The x86 build is an architecture check, not a supported release: it has not been run on a 32-bit Windows machine or checked with audio hardware. The current Rust MSVC target and CPAL's Windows backend require Windows 10 or newer, so this x86 target does not add Windows 7/8 support ([Rust MSVC target requirements](https://doc.rust-lang.org/rustc/platform-support/windows-msvc.html), [CPAL minimum Windows version](https://github.com/RustAudio/cpal/blob/master/CHANGELOG.md)). Windows 10 Home and Pro reached end of support in October 2025; the supported lifecycle for LTSC and other editions varies ([Microsoft lifecycle](https://learn.microsoft.com/en-us/lifecycle/products/windows-10-home-and-pro)). A 32-bit app can run under WOW64 on 64-bit Windows, but process and plug-in bitness still constrain memory use and in-process plug-in loading ([Microsoft WOW64 overview](https://learn.microsoft.com/en-us/windows/win32/winprog64/running-32-bit-applications)). Keep x64 as the release default; evaluate an optional x86 release only if users with 32-bit Windows hardware need it and it passes separate runtime, device, and performance checks.

UI styling is centralized in `crates/opentrack-app/src/theme.rs`. `ThemePreference::System` uses eframe/winit's Windows app-theme detection at startup and ThemeChanged events while running, and native window decorations follow the system. Both theme variants retain neutral surfaces; menus inherit the active visuals, and custom-painted track, MIDI, and mixer elements derive their colors from the current UI palette. Segoe UI is loaded from the installed Windows Fonts directory with embedded fonts as fallback; no Windows font is redistributed. These are egui-drawn controls, not native Win32 widgets. Windows accent-color and high-contrast integration have not been implemented. Theme-event tests cover light/dark/light transitions; real Windows setting changes and visual matching remain manual acceptance steps.

Logical framework key events merge top-row digits with numpad digits. A small Win32 subclass on the app window captures physical keys and modifiers so reference keypad bindings remain distinct; it does not install a global keyboard hook. This message adapter and atomic project-file replacement are the documented OS FFI boundaries. Keep command and workspace behavior in framework-independent Rust core types.

Each RWP file stores up to nine named project workspaces and project-specific preset collections. The app supports switching and locking these layouts, including Alt+Numpad1..9, Alt+Numpad0, and Ctrl+Numpad0. The organizer saves and creates global or project presets, copies global presets into a project, and supports idempotent auto-instantiation through application settings. The main window and project-specific child windows are recorded; exact Cubase window-role behavior, monitor identity, display-scale behavior, and reference measurements still need capture and validation.

Native project writes use a temporary sibling file and replacement. On Windows, the app calls MoveFileExW through windows-sys with replace-existing and write-through flags. See native-project-format.md for details.
